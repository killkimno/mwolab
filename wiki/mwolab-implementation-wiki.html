MwoLab 구현 위키

기준일 2026-07-24 · 현재 저장소 구현 기준

이 문서는 MwoLab의 현재 구조, 계산 기준, UI 동작과 수정 시 주의사항을 한곳에 모은 내부 구현 가이드다.

문서 운용 원칙
구현 전에는 관련 위키 내역을 참고한다. 단, 현재 코드와 새로 추출한 게임 데이터가 항상 우선하며 위키와 충돌하면 실제 구현을 확인한 뒤 판단한다. 사용자가 기능 구현이나 코드 수정을 명령하면 작업 완료 후 재사용 가능한 규칙이 추가·변경·명확화되었는지 판단하고, 필요하면 별도의 “위키 갱신” 요청을 기다리지 않고 같은 작업에서 즉시 위키도 갱신한다. 모든 작업 뒤 기계적으로 갱신하는 것은 아니다. 이 파일은 앱과 분리된 내부 문서이며 사용자가 요청하지 않는 한 앱에 링크를 추가하지 않는다.

현재 상태

MwoLab은 MechWarrior Online의 로컬 게임 데이터를 정적 JSON으로 변환해 사용하는 브라우저 기반 멕 피팅·정보·비교 도구다. 별도 프레임워크나 서버 API 없이 public 폴더만으로 배포할 수 있다.

공통 규칙

  • 근거 우선순위: 사용자의 최신 요구 → 현재 코드의 실제 동작 → 새로 추출한 게임 데이터 → 이 위키의 기존 설명 순서로 판단한다. 위키는 구현 가이드이지만 코드나 게임 데이터를 덮어쓰는 원본은 아니다.
  • 동일 계산: 정보보기·비교하기·통계·멕랩에서 같은 수치를 보여 줄 때는 같은 원본 데이터, 정규화 함수, 쿼크 계산을 재사용한다.
  • 데이터 우선: 멕, 장비, 로드아웃, 옵니포드 수치는 이름별 하드코딩보다 public/data의 속성과 재사용 인덱스에서 가져온다.
  • 선택 상태: 주 탭은 state.activeMainTab을 기준으로 하며, 멕랩과 정보보기의 선택 멕은 state.selectedMechIdsByTab에서 탭별로 따로 기억한다. state.selectedMech는 현재 활성 탭 선택의 작업용 값, state.currentBuild와 state.mechlabBuild는 현재 피팅, state.compareMechIds는 비교 대상, state.selectedStatsMechId는 통계 선택을 담당한다. 탭 전환만으로 다른 탭의 선택이나 피팅을 덮어쓰지 않는다.
  • 탭 수명주기: 숨겨진 주 탭은 불필요하게 미리 렌더링하지 않는다. 탭 전환 시 그 탭에 필요한 렌더 함수만 호출하고 URL의 멕 및 tab 상태와 동기화한다.
  • 표현 일관성: 하드포인트 태그, 멕 슬롯, 쿼크 색상, 숫자 단위와 빈 값 표시는 화면마다 별도로 복제하지 말고 공용 렌더링 규칙을 따른다.
  • 성능: 추출 데이터는 게임 갱신 전까지 정적이라고 보고 반복 파생값을 브라우저 메모리에 캐시한다. 선택만 바뀌는 경우 전체 목록을 재계산하거나 재생성하지 않는다.
  • 검증: 수정한 범위의 구문, 데이터 구조, 계산 회귀, git diff --check를 확인한다. 사용자가 요청하지 않으면 로컬 미리보기 서버를 시작하거나 검사하지 않는다.

구조와 데이터 흐름

HTML이 화면 골격을 제공하고, 하나의 전역 상태 객체를 중심으로 app.js가 데이터 로딩·계산·렌더링·이벤트를 처리한다. MWO 로드아웃 문자열 변환만 mwo-codec.js에 분리되어 있다.

MWO 설치 파일 → extract_mwo_data.py → public/data/*.json → init() → state → 계산 함수 → 화면 렌더링
  1. init()이 index.json과 멕·장비·로드아웃·옵니포드 JSON을 읽는다.
  2. 읽은 데이터는 state에 저장되고, 검색·쿼크·하드포인트용 파생 인덱스는 브라우저 메모리 캐시에 만든다.
  3. 멕 선택 시 기본 로드아웃 또는 저장된 빌드를 currentBuild로 구성한다.
  4. calculateBuild()가 중량, 슬롯, 아머, 장비, 탄약, 엔진, 발열과 경고를 계산한다.
  5. 각 탭의 렌더 함수가 동일한 원본 데이터와 계산 기준을 사용해 화면을 갱신한다. 보이지 않는 주 탭은 미리 렌더링하지 않는다.

추출된 숫자는 게임 데이터 갱신 전까지 사실상 정적이다. 반복 계산이 큰 값은 JSON에 다시 저장하지 않고 브라우저 메모리에서 캐시한다.

멕랩 탭

세부 카테고리: 멕 탐색, 빌드 헤더, 컴포넌트, 장비 목록, 업그레이드, 피팅 요약, 로컬 저장·MWO 코드, 사격 시뮬레이션.

  • 멕 탐색: 검색, 진영, 체급, 톤수 정렬과 큰/작은 목록을 지원한다. 기종과 변형을 그룹화하며 공용 멕 슬롯과 하드포인트 태그를 쓴다. 목록의 체급 헤더는 눈에 띄는 상위 카테고리 슬롯으로 표시하고, 진영 헤더는 그 아래의 작은 보조 구분으로 표시한다.
  • 멕 종류 필터: definition.stats.VariantType이 없으면 일반형, Hero와 Champion은 각각 히어로와 챔피언으로 분류하며 그 밖의 값은 스페셜로 분류한다. 스페셜 하위 타입은 현재 멕 데이터에서 동적으로 만들고 기본 선택하며, 첫째 줄의 스페셜이 선택된 동안에만 조작할 수 있다. 하위의 모두 토글은 모든 스페셜 타입을 한 번에 선택하고, 모든 타입이 선택됐을 때만 체크 상태가 된다. 첫째 줄과 스페셜 하위 줄 모두 개별 선택을 전부 끄면 빈 선택으로 두지 않고 해당 줄의 모두 상태로 자동 복귀한다. 필터 선택지는 왼쪽 사각형에 체크 표시가 나타나는 체크박스형 토글로 표현한다.
  • 필터 탭: 진영·체급·멕 종류·하드포인트 필터는 상단의 기본 탭에 두고, 특수 쿼크·특수 스탯·특수 장비 필터는 특수기능 탭에 둔다. 탭을 바꿔도 두 탭의 선택 상태와 필터 적용 상태는 유지한다.
  • 하드포인트 필터: 에너지·미사일·발리스틱·AMS·ECM·JJ·MASC를 서로 독립적으로 활성화한다. 비활성 종류는 필터링하지 않으며, 에너지·미사일·발리스틱·AMS의 전체·RA·RT·HD·LT·LA 입력값은 모두 해당 위치의 하드포인트 수에 대한 최솟값이다. 한 종류에 여러 최솟값을 입력하면 전체와 모든 부위 조건을 동시에 만족해야 한다. ECM과 JJ는 전체 최솟값만 입력하며, MASC는 활성화 시 전체 1 조건으로 고정한다. JJ는 쿼크를 포함한 최대 점프젯 수, MASC는 장착 가능 여부를 사용한다. 옵니멕은 기본 로드아웃의 옵니포드를 합성한 유효 정의를 사용하고 결과는 멕별 브라우저 메모리에 캐시한다.
  • 특수기능 필터: 특수 사항과 특수 장비는 각각 독립된 모두 상태와 선택 집합을 가진다. 한 패널에서 개별 항목을 선택해도 다른 패널의 모두 상태는 바뀌지 않는다. 각 패널 안에서는 개별 항목을 복수 선택할 수 있고 선택 항목 중 하나 이상을 가진 멕을 표시하며, 마지막 개별 항목을 끄면 그 패널만 모두로 자동 복귀한다. 두 패널에 모두 개별 조건이 있으면 특수 사항 조건과 특수 장비 조건을 동시에 만족해야 한다. 점프젯 흔들림 없음은 shake_damping_mechs.json, 잼·낙하·크리티컬·환경 열 면역은 기본 옵니포드를 포함한 유효 쿼크, 컴팩트 장비·Tacticon·방패·Partial Wing·특수 타겟컴은 고정 장비, 강화된 점프젯은 같은 섀시의 전체 옵니포드 고정 장비를 사용해 판별한다. Upper Arm 액추에이터 없음은 좌우 팔 중 하나 이상이 Shoulder만 있고 Upper/Lower Arm 및 Hand Actuator가 없는지 판별한다. 옵니멕은 각 변형의 기본 장착 옵니포드를 합성한 팔 정의만 검사하므로 해당 포드를 실제 장착한 변형에만 적용하며, 같은 섀시 전체로 확장하는 강화된 점프젯 규칙과 구분한다. 특수 무기는 진영을 무시하는 Clan AC/20(NobleAutoCannon20, C-AC/20 제외), Railgun, Arrow IV 계열 무기가 기본 기체 또는 기본 옵니포드에 실제 고정 장착됐는지 판별한다. Supercharger는 실제 Supercharger 장비, MASC + Supercharger는 실제 결합 장비 또는 SuperchargerDummy가 기본 기체나 기본 옵니포드에 고정 장착됐는지만 판별한다. 판별 결과는 멕별 브라우저 메모리에 캐시한다. 각 토글에는 기능 이름과 효과·판별 기준을 설명하는 짧은 보조 문구를 함께 표시하며, 필터 대화상자의 크기는 탭 내용과 관계없이 고정한다.
  • 호버 미리보기와 실제 선택 상태는 분리한다. 호버 종료 후 선택 멕이 복원되어야 한다.
  • 빌드 헤더: 선택 변형, 진영, 톤수, 속도 범위와 Stock/Save/Clear 등 현재 빌드 동작을 한곳에서 관리한다.
  • 컴포넌트: 고정 장비, 이동식 장비, 아머, 슬롯, 하드포인트, 옵니포드를 부위별로 표시하고 모든 장착 경로에 같은 검증을 적용한다.
  • 장비 목록: 무기·탄약·엔진·모듈 하위 카테고리와 검색·정렬을 제공한다. 현재 멕이 장착할 수 없는 계열은 필터링한다.
  • 업그레이드: 아머·스트럭처·히트싱크·아르테미스 상태를 빌드에 저장하고 관련 장비 ID와 계산값을 함께 바꾼다.
  • 피팅 요약: 중량, 아머·스트럭처, 속도, 냉각, 점프 높이, ALPHA, HEAT, DPS, 탄약과 경고를 calculateBuild() 결과로 표시한다. 중량 계산에는 이동 장비와 고정 장비뿐 아니라 components[].internals의 톤수 보정값도 포함한다. Compact Gyro의 tons 값은 기본 Gyro 대비 추가 중량이므로 항상 총중량에 양수로 더한다. 예를 들어 1.5는 +1.5t이다. Compact Cockpit과 XL Gyro의 음수 톤수, 내부형 방패 등의 톤수 보정도 각각 원래 부호대로 실제 총중량에 반영한다.
  • 저장과 코드: 이름 있는 로컬 빌드와 멕별 저장 빌드를 분리하고 MWO 코드 입출력 후에도 같은 장착 검증을 거친다.
  • 시뮬레이션: 현재 빌드의 무기만 사용하며 실제 피팅 쿼크, 탄약, 잼, 고스트 힛과 발열 조건을 반영한다.

정보보기 탭

세부 카테고리: 종합 내구도, 기동성, 스트럭처, 아머, 엔진, 쿼크 서머리, 상세 쿼크.

  • 현재 selectedMech의 기본 로드아웃으로 유효 멕 정의를 구성한다. 멕랩에서 임시 편집 중인 장비 구성을 정적 멕 사양처럼 섞지 않는다.
  • 피팅하기는 정보보기 탭에 기억된 현재 선택 멕 ID를 멕랩 선택으로 넘긴 뒤 해당 멕의 피팅을 연다.
  • 쿼크 적용 체크는 내구도와 기동성의 최종값 및 쿼크 요약에 같은 기준으로 반영한다.
  • 종합 내구도·스트럭처·아머는 같은 부위 순서와 동일한 합계 기준을 쓴다.
  • 기동성은 속도, 가속, 감속, 선회, 몸통 각도·회전속도를 공용 계산에서 가져온다. MASC 값은 정의된 최종값 규칙을 따른다.
  • 쿼크 서머리는 상세 QUIRKS 목록에 넣지 않고 독립 카드로 표시한다.
  • 통계 상세 패널이 정보보기 카드를 재사용할 때도 값과 표현이 달라지지 않아야 한다.

무기정보 탭

세부 카테고리: 무기, 모듈, 고스트 힛.

  • 무기: 장비 JSON의 원본 수치에서 피해, 사거리, 속도, 발열, 쿨다운, DPS·DPH, 탄약, 산포, 잼 등의 파생 통계를 계산한다.
  • 모듈: 엔진·히트싱크·점프젯·MASC·전자장비 등 무기가 아닌 장비를 종류별로 보여 주며 없는 속성을 억지로 0으로 만들지 않는다.
  • 고스트 힛: heatPenaltyID 그룹과 개별 그룹을 분리하고 동시 발사 수별 추가 발열을 보여 준다. 외부 위키 표를 수치 원본으로 쓰지 않는다.
  • 하위 탭과 표 정렬 상태는 state에 보존한다. 데이터와 정렬 조건이 같으면 렌더 HTML 캐시를 재사용한다.
  • 표시명은 현지화를 쓰되 계산과 매칭은 정규화한 내부 이름·ID·원본 속성을 사용한다.

비교하기 탭

세부 카테고리: 선택 목록, 기준 멕, 차이 표시, 내구도, 기동성, 엔진·기본 정보, 쿼크 요약.

  • 최대 15개 멕을 compareMechIds에 유지하고 동일 멕을 중복 추가하지 않는다. 전체 지우기와 개별 제거를 지원한다.
  • 각 멕은 정보보기와 같은 기본 로드아웃·유효 정의·쿼크 계산으로 비교 엔트리를 만든다.
  • 기준 멕이 있으면 그 멕과의 차이를, 없으면 행의 최대·최소를 기준으로 상승·하락 색과 기호를 표시한다.
  • 값이 클수록 좋은 항목과 작을수록 좋은 항목의 순위를 구분하고 동률은 같은 순위로 처리한다.
  • 쿼크 적용 전환은 비교 대상 전체에 동시에 적용한다. 정보보기·통계와 계산식이 달라지지 않아야 한다.
  • 스크롤 시 열 제목을 유지하는 고정 헤더 오버레이와 실제 표의 열 너비를 동기화한다.

통계 탭

세부 카테고리: 내구도, 기동성, QUIRKS, 세부 범위, 전체 목록·조건 필터, 개별·기종별 순위, 상세 패널.

  • 내구도: 총합·아머·스트럭처와 전체·몸통·어깨·개별 부위 범위를 지원한다.
  • 기동성: 가속, 감속, 선회 속도, 몸통 회전속도를 같은 단위와 정렬 방향으로 비교한다.
  • QUIRKS: 쿨다운, 발열, 내구도, 사거리, 탄속과 각 하위 스코프를 공용 쿼크 요약 함수에서 가져온다.
  • 순위 방식: 개별 변형과 기종별 집계를 구분한다. 기종별은 평균·최대·최소 집계 방식을 명시적으로 적용한다.
  • 필터: 전체 목록 또는 조건 필터를 선택하고 진영·체급·톤수·값 범위를 기존 순위 조건에 포함한다.
  • 멕 요약은 데이터 로드 후 유휴 시간에 작은 묶음으로 미리 계산하며 카테고리·필터·집계별 결과를 브라우저 메모리에 캐시한다.
  • 순위 조건이 같으면 기존 목록 DOM을 재사용하고, 멕 선택 시 이전·새 활성 행과 상세 패널만 갱신한다.
  • 화면 밖 행은 content-visibility와 레이아웃 격리로 불필요한 배치·페인트를 줄인다.
  • 통계 멕 슬롯은 공용 하드포인트 태그의 개수, JJ, MASC를 모두 표시한다. 체급과 슬롯 배경은 통계 전용 표현을 유지한다.

멕랩에 사용되는 룰

이 장은 멕랩 탭의 실제 피팅과 계산에 적용되는 도메인 규칙을 모은다. UI 배치는 탭별 가이드를 따르고, 장착 가능 여부와 수치는 아래 피팅·쿼크·무장·고스트 힛·시뮬레이션 규칙을 따른다.

멕 + 기본/저장 빌드 → 유효 차체·옵니포드 정의 → 장착 검증 → 쿼크 적용 → 피팅 합계 → 경고·툴팁·시뮬레이션
  • 장착·제거·드래그·자동 장착·MWO 코드 가져오기는 모두 같은 빌드 구조와 검증 함수를 사용한다.
  • 장비 이름으로 예외를 만들기 전에 장비 ID, hardpoint_type, stats.type, 탄약 타입과 원본 특수 속성으로 표현할 수 있는지 확인한다.
  • 멕랩 요약은 최종 빌드 계산의 결과이며 화면에 보이는 슬롯을 다시 세어 별도 합계를 만들지 않는다.
  • 고정 장비와 이동식 장비, 차체와 옵니포드 출처를 잃지 않아야 하드포인트 점유와 중복 내부 장비를 정확히 계산할 수 있다.

피팅·슬롯 규칙

컴포넌트 순서

Head → Left Arm → Left Torso → Center Torso → Right Torso → Right Arm → Left Leg → Right Leg 순서를 유지한다. 후방 토르소 아머는 독립 장비 카드가 아니라 아머 계산에만 포함한다.

슬롯과 하드포인트

  • 사용 슬롯 = 컴포넌트 내부 고정 항목 수 + 장착 아이템의 stats.slots 합계다.
  • 슬롯 한도는 컴포넌트의 slots를 사용한다.
  • 무기 장착 수용량은 하드포인트의 weapon_slots를 사용한다. 원본 MDF의 Slots 속성은 무기 개수가 아니다.
  • weapon_slots 매핑이 실제로 없는 경우에만 1을 폴백으로 사용한다.
  • 옵니멕은 현재 장착한 옵니포드 하드포인트를 최우선으로 사용한다.
  • 옵니멕의 차체 고정 무기는 옵니포드 하드포인트를 점유하지 않지만, 옵니포드 자체의 고정 무기는 해당 하드포인트를 점유한다. 계산과 장착 검증에서 고정 장비의 출처를 함께 보존한다.
  • 차체와 옵니포드가 제공하는 내부 고정 장비는 같은 ID라도 각각의 실제 장착분이므로 중복 제거하지 않는다.
  • 옵니포드 귀속 장비, SHOULDER·HIP 같은 내부 고정 슬롯, XL 엔진 측면처럼 사용자가 움직일 수 없는 슬롯은 고정 옵니 엔진과 같은 그라데이션 없는 단색 진회색 블록으로 표시한다. 이동식 슬롯보다 어두운 배경, 저채도 글자, 굵은 좌측 고정 레일과 내부 테두리를 사용해 빈 슬롯 및 이동식 장비와 구분한다.
  • 장착 후 위치가 확정되어 움직일 수 없는 아머·스트럭처 업그레이드 점유 슬롯도 좌측 고정 레일, 내부 테두리, 굵은 글자 규칙을 따른다. 좌측 레일과 글자는 일반 고정 슬롯의 회색을 사용하고, 아머와 스트럭처의 점유 배경·테두리도 같은 차콜 회색 계열로 통일한다. 아직 점유되지 않은 업그레이드 슬롯에는 적용하지 않는다.
  • 스텔스 아머는 좌우 팔, 좌우 몸통, 좌우 다리에 각각 2칸씩 총 12칸을 고정 점유한다. 이 슬롯은 다른 부위로 이동하거나 장비 장착 시 밀려나지 않으며, 어느 부위든 필요한 2칸이 부족하면 해당 부위 슬롯 초과와 아머 업그레이드 슬롯 부족을 경고한다. 머리와 중앙 몸통에는 스텔스 아머 슬롯을 배치하지 않는다.
  • 하드포인트 ID는 선행 0을 제거해 정규화한 뒤 비교한다.

장비 필터와 장착

  • 에너지·미사일·발리스틱·AMS는 해당 유효 하드포인트가 있을 때만 목록에 표시한다.
  • ECM, 점프젯, MASC는 멕 능력과 톤수 조건을 모두 만족해야 한다.
  • C.A.S.E., Active Probe, Target Computer처럼 원본 데이터에 장착 수량이나 허용 부위가 지정된 장비는 그 제한을 검증한다.
  • 드래그 앤 드롭과 클릭 자동 장착은 동일한 dropValidation 규칙을 거친다.
  • 장착 후 중량 초과, 슬롯 초과, 하드포인트 부재, 엔진 범위, 장비 수량 제한을 계산해 경고한다.

업그레이드와 MWO 코드

  • 아머, 스트럭처, 히트싱크, 아르테미스 업그레이드를 빌드 상태로 관리한다.
  • 아르테미스 적용/해제 시 표시 이름만 바꾸지 않고 무기와 탄약 ID를 양방향으로 교체한다.
  • 표준 → 아르테미스 → 표준 왕복 후 원래 ID가 복원되어야 한다.
  • alwaysHasArtemis 무기는 선택형 변환 대상이 아니다.
  • mwo-codec.js는 6비트 문자 형식의 직렬화만 담당하고, 실제 멕·장비 검증은 app.js에서 한다.

쿼크 규칙

  • 쿼크 이름과 무기 검색 키는 대소문자를 구분하지 않도록 정규화한다.
  • 요약 값은 일반 쿼크 + 무기 계열 쿼크 + 가장 잘 맞는 무기 전용 쿼크를 합친다.
  • 쿨다운·발열·지속시간·산포처럼 감소가 이득인 multiplier는 음수로 저장되므로 Math.max(0, -value)로 요약한다.
  • 사거리·탄속·열 방출·ROF처럼 증가가 이득인 multiplier는 Math.max(0, value)로 요약한다.
  • 무기 전용 쿼크는 통계 접미사를 제거한 이름을 장비의 이름·표시 이름·별칭과 매칭한다.
  • 무기 계열은 개별 이름 하드코딩보다 장비 데이터의 hardpoint_type 또는 stats.type을 우선한다.

요약 카드

  • 쿨다운: MAX, ENERGY, MISSILE, BALLISTIC.
  • 발열: MAX, ENERGY, MISSILE, BALLISTIC, HEAT DISSIPATION.
  • 사거리·탄속: MAX, ENERGY, MISSILE, BALLISTIC.
  • 듀레이션/ROF: 레이저 듀레이션과 가장 높은 ROF를 5% / 3% rof 형태로 한 행에 표시한다.
  • 산포: 에너지 항목이 없지만 시각 정렬을 위해 빈 위치를 유지한다.
  • 내구도: 부위별이 아니라 MAX(아머+스트럭처), 아머, 스트럭처, 크리티컬 방지의 총합만 표시한다.
  • 특수: 현재 ECM, 점프젯, NARC 지속시간을 인식한다.

쿼크 서머리는 QUIRKS 목록 안이 아니라 독립 정보 카드다.

값 색상

기본값과 쿼크 기여도를 함께 표시하는 경우 최종값은 초록색, 쿼크 기여도는 노란색이다. 기본값, 괄호, 연산자는 주변 통계의 기본 색을 유지한다.

DPH와 MASC 툴팁

  • DPH는 발열 1점당 피해량(Damage Per Heat)이므로 damage / heat로 계산한다.
  • MASC 최종 기동성은 쿼크가 반영된 현재 값에 MASC 부스트를 곱한다: 쿼크 최종값 × (1 + MASC boost).
  • MASC 부스트가 0인 항목은 부스트 행과 최종값 행을 모두 표시하지 않는다.
  • 멕 핏팅의 점프젯 높이는 연소시간과 초기 추력 쿼크가 반영된 최종 수치로 계산하며, 요약에는 최종 결과만 표시한다.

에너지 레이저 예외

레이저 전용 쿼크는 레이저 무기에, 에너지 쿼크는 모든 에너지 무기에 적용한다. PPC도 에너지 쿼크의 영향을 받는다. 이름에서 구분되는 경우 표준 레이저 쿼크를 ER 또는 펄스 변형에 섞지 않는다.

무기 계산 규칙

피해와 연속 무기

  • 직격 피해는 기본적으로 damage × numFiring × 발사체 수다.
  • 탄환형 펠릿 무기는 numPerShot을 발사체 수에 반영한다.
  • 스플래시 총피해는 직격 + 양옆 부위의 스플래시를 합산한다.
  • 머신건·로터리 AC는 직격 피해 × ROF를 초당 피해로 표시하고 ROF 쿼크를 반영한다.
  • 레이저·화염방사기처럼 원본 피해가 초당 값인 연속 무기는 ROF를 다시 곱하지 않는다.
  • 레일건 커패시터 등 항상 적용되는 무기 모듈 보너스는 동일 진영의 장비 데이터에서 찾아 피해와 발열에 합산한다.

사거리와 특수 통계

  • 툴팁 사거리 순서는 MIN RANGE, OPTIMAL RANGE, MAX RANGE, VELOCITY다.
  • 사거리 쿼크는 MIN RANGE를 늘리지 않는다.
  • ATM은 60~349m, 350~649m, 650~1100m의 피해 구간을 사용하며 사거리 쿼크는 구간 상한과 최대 사거리에 반영한다.
  • 산포, 크리티컬 확률·피해, 대상 발열, 차지 시간은 데이터가 있을 때 별도 통계로 표시한다.
  • Ultra AC는 잼 지속시간, 잼 확률, 기대 DPM을 표시하며 관련 쿼크를 반영한다.

탄약

  • 탄약량은 장착 탄약 레코드의 stats.numShots를 사용하며 반톤과 1톤을 따로 존중한다.
  • 활성 탄약 타입은 선택형 아르테미스 적용 시 artemisAmmoType, 그 외에는 ammoType이다.
  • 동일한 정규화 탄약 타입을 쓰는 무기들은 탄약 풀을 공유한다.
  • 동시 발사 가능 횟수는 매칭되는 탄약통의 합계를 묶인 무기들의 총 ammoPerShot으로 나눈다.
  • 탄약에도 적용되는 전용 무기 쿼크를 장비 필터와 비교 통계에 일관되게 반영한다.

고스트 힛

데이터와 계산 규칙

  • 외부 웹사이트의 표를 수치 원본으로 사용하지 않는다. 무기별 기본 발열, 페널티, 발생 시점, 그룹은 equipment.json의 heat, heatpenalty, minheatpenaltylevel, heatPenaltyID에서 읽는다.
  • 같은 heatPenaltyID의 무기를 동시에 발사해 무기별 발생 시점을 넘으면 고스트 힛 후보를 계산한다. 개별 그룹은 같은 무기끼리만 영향을 준다.
  • 같은 그룹 안에서도 AC/20과 Clan AC/20처럼 발생 시점이 다를 수 있고, AC/20과 Ultra AC/20처럼 추가 발열도 다를 수 있다.
  • 동시에 발생한 후보 중 가장 높은 추가 발열 하나만 기본 발열 합계에 더한다.
  • 고정 단계 상승 곡선은 코드에 두되, 무기별 수치와 그룹은 JSON에서 가져온다.
  • HSL 쿼크는 *_minheatpenaltylevel_additive 값을 사용한다. Ballistic·Energy·Missile 계열 HSL과 별칭으로 매칭되는 무기·패밀리 전용 HSL을 합산한다.
  • HSL은 고스트 힛 발생 여부를 검사하는 임계치만 뒤로 미룬다. 발생한 뒤에는 원래 임계치부터 현재 무기 수까지의 상승 단계를 모두 적용하므로 추가 발열 수치를 줄이지 않는다.
  • 예를 들어 임계치가 2인 AC/20은 HSL +1에서 2문 동시 발사로 발생하지 않지만, 3문 동시 발사에서는 원래 3문 단계의 추가 발열이 그대로 발생한다.

무장 정보

  • 그룹별 표에는 무기마다 각 동시 발사 수에서 생기는 추가 발열만 표시한다.
  • 그룹명은 IS MRM/SRM GROUP, IS ROTARY AC GROUP, IS LRM/THUNDERBOLD GROUP 등을 사용한다.
  • 공유 그룹이 없는 무기는 개별 그룹 - 개별 그룹으로 서로 영향 없음으로 표시한다.
  • 설명은 최고 추가 발열 적용 규칙과 AC/20 계열, AC/10 ×2 + Ultra AC/10 ×1 예시로 요약한다.

멕랩 표시

  • 현재 피팅의 유효 HSL을 반영한 뒤 고스트 힛 발생 조건을 만족하면 슬롯 영역 왼쪽 위에 경고 아이콘을 오버레이한다. 아이콘 표시 여부는 슬롯 위치를 바꾸지 않는다.
  • 발생 그룹에 참여하는 이동식·고정 무장 슬롯에는 빨간 외곽선을 표시한다.
  • 경고 아이콘 툴팁은 발생 그룹마다 한 줄씩 무기 구성 : 발열 88.8% (최종: 00.00, 고스트 힛: 00.00) 형식으로 표시하며 내용에 맞춰 폭을 정한다.
  • 발열 퍼센트는 쿼크 적용 후 무기 발열 합계와 고스트 힛을 더한 최종 발열이 현재 멕의 최대 발열 허용량에서 차지하는 비율이다. 현재 누적 발열은 포함하지 않는다.
  • 발열 퍼센트는 경고색 굵은 글씨, 고스트 힛 수치는 빨간색 굵은 글씨로 표시한다.
  • 발생 슬롯의 HEAT 툴팁은 최종 결과 모드에서 최종수치 + 고스트 힛, 쿼크 수치 모드에서 최종수치(쿼크수치) + 고스트 힛, 모든 수치 모드에서 최종수치(원본 ± 쿼크) + 고스트 힛 순서로 표시한다.
  • 멕랩의 ALPHA, HEAT, DPS 기본 수치에는 고스트 힛을 합산하지 않는다.

사격 시뮬레이션

현재 빌드에 장착된 무기를 가져와 브라우저 애니메이션 프레임으로 사격, 쿨다운, 발열, 냉각, 잼과 피해 누적을 계산한다.

  • 사격 그룹 할당과 누름 상태를 관리하며 그룹별 시각 상태를 갱신한다.
  • 거리, 이동 상태, 맵 온도, 스플래시 적용, 과열 시 종료를 시나리오 조건으로 사용한다.
  • 일반 발사, 연속 피해, 번(burn), 연발 대기 탄환을 각각 처리한다.
  • 쿨다운·발열·사거리·ROF·무기 전용 쿼크와 타겟 컴퓨터 보너스를 적용한다.
  • 같은 시점에 발사된 무기를 고스트 힛 그룹별로 묶고 HSL로 보정된 발생 시점을 검사한 뒤 그룹에서 가장 높은 추가 발열을 시뮬레이션 열에 적용한다.
  • 고스트 힛 추가 발열은 JSON 원본 무기 발열과 쿼크 미적용 기본 사이클로 계산한다. HEAT·쿨다운·ROF 쿼크는 추가 발열 수치에 영향을 주지 않고 HSL만 발생 시점을 늦춘다.
  • 경과 시간, 총 피해, DPS, 발열은 무기 발사 컨트롤 바로 위에 함께 둔다.
  • 시뮬레이션 UI는 게임 배치에 가깝게 하되 시야와 즉시 판독성을 우선한다.

JSON 파서 법

게임 아카이브를 브라우저 JSON으로 만드는 추출 단계와 앱이 JSON을 읽어 계산 가능한 형태로 정규화하는 소비 단계를 함께 관리한다. 생성 JSON은 원본에 가까운 교환 데이터이며 화면별 파생 요약 저장소가 아니다.

브라우저 로딩과 결합

  • index.json에서 생성 파일 경로와 개수를 읽고 mechs.json, equipment.json, loadouts.json, omnipods.json을 로드한다.
  • 멕, 장비, 로드아웃, 옵니포드는 숫자 ID의 표현이 달라도 찾을 수 있도록 조회 경계에서 문자열 또는 정규화 키로 통일한다. 원본 ID 자체는 임의로 바꾸지 않는다.
  • 이름 매칭은 대소문자, 공백, 구분 기호 차이를 정규화한 검색 키를 사용한다. 표시 이름은 UI에만 사용하고 내부 이름·ID를 기본 결합 키로 둔다.
  • 누락 속성은 undefined, null, 빈 문자열을 구분해 처리한다. 의미가 확인되지 않은 누락값을 0, 빈 배열 또는 다른 레코드로 조용히 대체하지 않는다.
  • 숫자 필드는 계산 경계에서 유한 숫자로 변환하고, 퍼센트 multiplier의 부호 의미는 쿼크 종류별 규칙에 따라 해석한다.
  • 멕과 기본 로드아웃은 멕 ID로, 장비 장착 항목은 장비 ID로, 옵니포드는 현재 set과 component 또는 확정된 현재 ID로 결합한다.
  • 옵니멕의 유효 정의는 기본 차체를 복사한 뒤 현재 빌드의 부위별 옵니포드 하드포인트·내부 장비·고정 장비·쿼크를 합성한다. 원본 JSON 객체를 화면 상태 변경으로 직접 변형하지 않는다.

하드포인트와 장비 정규화

  • 하드포인트 타입은 대소문자를 제거해 energy, missile, ballistic, ams, ecm 등의 공용 키로 변환한다.
  • 하드포인트 ID는 선행 0을 제거해 비교한다. 예를 들어 "02"와 2는 같은 ID다.
  • 무기 수용량은 직접 WeaponSlot 자식 수를 추출한 weapon_slots를 사용한다. 매칭 자체가 없는 경우에만 1을 폴백한다.
  • 무기 계열은 가능한 경우 hardpoint_type 또는 stats.type으로 판정한다. 레이저·PPC·미사일·발리스틱 이름 목록을 코드에 반복해서 만들지 않는다.
  • 탄약 풀은 정규화한 활성 탄약 stats.type으로 결합한다. 선택형 아르테미스는 무기의 artemisAmmoType, 일반 상태는 ammoType을 쓴다.
  • 파생 검색 인덱스, 쿼크 요약, 하드포인트 배지와 통계 엔트리는 로드 후 브라우저 메모리에서 만들며 생성 JSON에 역으로 기록하지 않는다.

게임 데이터 추출

의도적인 게임 데이터 갱신은 반드시 tools/extract_mwo_data.py를 사용한다.

원본용도
Game/GameData.pak멕 목록, 장비, 로드아웃, 아르테미스 원본 속성
Game/Localized/English_xml.pak표시 이름과 현지화 텍스트
Game/mechs/*.pak차체·옵니포드 상세 정의, Cockpit 속성, 하드포인트 WeaponSlot 수

전체 추출

python tools/extract_mwo_data.py --game-dir "F:\Game\Steam\steamapps\common\MechWarrior Online" --out public\data

하드포인트만 갱신

python tools/extract_mwo_data.py --game-dir "F:\Game\Steam\steamapps\common\MechWarrior Online" --out public\data --hardpoints-only

전체 추출은 설치된 게임의 모든 데이터를 다시 읽기 때문에 요청 범위 밖의 밸런스 값이나 숫자 형식도 바뀔 수 있다. 하드포인트 수정만 필요하면 --hardpoints-only로 기존 장비·로드아웃 데이터를 보존한다.

전체 추출은 모든 MDF의 Cockpit.ShakeDamping을 검사하고 값이 정확히 1.0인 멕을 shake_damping_mechs.json 하나에 모은다. 항목에는 멕 식별 정보, 원본 값, PAK와 MDF 경로를 보존하며, 속성이 누락된 멕이나 최상위 Mech.ShakeDamping 값은 이 목록에 포함하지 않는다.

NULL 옵니포드 처리

  • 기본 로드아웃에서 옵니포드 값이 없거나 NULL이면 후면 장갑 가상 컴포넌트를 제외하고 멕 기종과 컴포넌트를 검사한다.
  • 몸통 해석은 고정 순서로 수행한다. 동일 이름 세트 → 사용자 확정 숫자·normal_body·shared_body 기록 → 이름 끝 글자를 하나씩 제거해 찾은 일반형과 그 확정 기록 → 미해결 일반형의 비일반형 예상 후보 보고 → 미확정 보고 분류 순서다.
  • 정규화한 멕·기본 로드아웃 이름과 옵니포드 set 이름이 같고 같은 컴포넌트의 후보가 정확히 하나이면 자동 할당한다. 여러 개이면 데이터 오류로 중단한다.
  • 동명 후보가 없으면 tools/omnipod_null_resolutions.json의 사용자 확정 기록을 적용한다. 숫자 ID를 그대로 신뢰하지 않고 새로 추출한 set과 컴포넌트로 현재 ID를 다시 찾는다.
  • normal_body는 사용자 확정 일반형 자체 몸통이며 컴포넌트 정의가 같은 파생형이 상속할 수 있다. shared_body는 다른 옵니포드와 몸통을 공유해 별도 숫자 레코드가 없는 사용자 확정 사례이며 값은 NULL로 유지한다.
  • 확정 기록도 없으면 이름 마지막 글자를 하나씩 제거해 일반형을 찾는다. 일반형의 고유 숫자 옵니포드 또는 사용자 확정 숫자·normal_body 기록을 컴포넌트 정의 일치 조건으로 상속한다.
  • 그래도 미해결인 일반형은 동일 섀시이면서 전체 일반형 이름으로 시작하는 비일반형의 고유 몸통 옵니포드를 예상 후보로 보고한다. 후보는 사용자가 확인하기 전에는 자동 적용하지 않는다.
  • 미확정 보고는 항상 미확정 - 예상 후보와 미확정 - 예상 후보 없음을 모두 표시하고, 모든 미확정 항목을 정확히 한 구역에 넣는다.
  • 현재 사용자 확정 숫자 매핑은 NTG-DCS→NTG-D, TBR-CS→TBR-C, TBR-SCS→TBR-S, ADR-W→ADR-WL, IFR-J→IFR-JL, NTG-H→NTG-HL, SMN-F→SMN-FL, SMN-M→SMN-ML, EXE-M→EXE-MTSP, SHC-NOLGD→SHC-NO, TBR-MTSP→TBR-M, WHK-KLGD→WHK-K다. HBR-F는 normal_body, MDD-SILGD와 VPR-SC는 shared_body로 기록한다.

전체 JSON 갱신 절차

  • 임시 출력에 전체 데이터를 추출한 뒤 JSON 구조, 옵니포드 NULL 해소 결과, 표준 멕과 옵니포드 하드포인트 회귀 기준을 검증하고 성공한 결과만 게시 데이터에 반영한다.
  • 새 멕 ID와 public/assets/mech-icons의 썸네일을 비교하고, 누락 이미지는 GameData.pak의 Libs/UI/Screens/Assets/MechIcons/에서 찾는다. 기존 썸네일은 덮어쓰지 않는다.
  • 갱신 보고에는 생성 JSON 범위, 자동·기록·공유 몸통 기반 NULL 해소, 두 미확정 구역, 추가된 썸네일과 검증 결과를 포함한다.
  • 미확정이나 해석 오류가 있으면 임시 결과를 게시하지 않는다. 모두 해결된 현재 전체 데이터는 멕 1,292개, 장비 751개, 로드아웃 1,315개, 옵니포드 1,833개이며 미확정과 누락 썸네일은 0건이다.
  • “전체 JSON 갱신”은 추출·검증·보고까지만 포함한다. 커밋, 푸시, GitHub Pages 배포는 별도의 명시적 요청이 있을 때만 수행한다.

추출 데이터 보존 원칙

  • 원본 속성은 덮어쓰지 않고 필요한 파생 필드를 추가한다.
  • 무기에는 ammoType, artemisAmmoType, alwaysHasArtemis를 보존한다.

  • 파생 요약과 캐시를 public/data/*.json에 영구 저장하지 않는다.
